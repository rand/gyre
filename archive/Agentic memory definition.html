Here is a tight definition and a practical breakdown.

What it is

Agentic memory is the structured, policy-driven store of information that an autonomous agent writes to, retrieves from, and prunes over time to improve decisions across tasks. It is not a raw log or a static KB. It is a selective, credited, and revisable substrate for behavior.

Formally, let memory be M=⟨I,πwrite,πretrieve,πconsolidate,πforget⟩M = \langle \mathcal{I}, \pi_{\text{write}}, \pi_{\text{retrieve}}, \pi_{\text{consolidate}}, \pi_{\text{forget}} \rangleM=⟨I,πwrite​,πretrieve​,πconsolidate​,πforget​⟩ where I\mathcal{I}I is a set of items with provenance, confidence, and scope. Policies control what gets stored, when it is recalled, how it is summarized, and what is discarded.

Types

  • Working memory – short-lived scratchpad for the current deliberation.

  • Episodic memory – timestamped observations, actions, outcomes, and rewards.

  • Semantic memory – stable facts, user preferences, tools, constraints.

  • Procedural memory – skills, plans, macros, heuristics, and learned controllers.

  • Meta-memory – statistics about what to store, when to fetch, and what to forget.

Minimum viable data model

Each item should have:

  • id, type, content, source, timestamp

  • confidence, utility score, lineage links, scope owner, TTL

  • indices: symbolic keys, vector embedding, and graph edges

Core mechanics

  • Write policy – gate on novelty, prediction error, or utility gain; dedupe by semantic similarity and key fields.

  • Retrieval policy – hybrid search that uses task intent, symbols, and vectors; rank by expected utility, not cosine alone.

  • Consolidation – periodic summarization and schema folding to reduce entropy while keeping causal links.

  • Forgetting – TTLs, decay schedules, rate limits, and size caps with eviction that respects provenance and utility.

  • Credit assignment – link items to outcomes so retrieval and write thresholds learn over time.

How it differs from adjacent things

  • Context cache – transient. Agentic memory persists with policies and credit.

  • Vector DB – an index, not a memory. Memory uses vectors plus symbols, graphs, and policies.

  • Knowledge base – curated and static. Agentic memory is operational and self-modifying.

Operational loop

  1. Observe → encode → candidate items

  2. Decide with retrieval selectors conditioned on goal and state

  3. Act → measure outcome → assign credit

  4. Consolidate and prune on a schedule

Quality and safety bar

  • Utility lift on target tasks, retrieval precision@k, false recall rate, latency, and bloat ratio

  • Provenance required for every item, scoped tenancy per user, reversible edits, explicit consent for personal data

  • Red team prompts that probe for leakage or spurious personalization

Anti-patterns

  • Hoarding everything or summarizing without sources

  • Vector-only recall for symbolic constraints

  • Personalization without scope and consent

  • Static memory that never learns write and fetch thresholds

If removing the memory does not measurably change decisions or outcomes, it was not agentic memory. If it changes them in ways you can attribute, monitor, and revise, it is.

Here is a clean way to unify “memory” with on-demand retrieval and tool use so the agent always assembles the right context under real budgets.

Unifying idea

Treat everything the agent might put into the prompt as a context candidate with the same schema and the same selection logic, regardless of origin: long-term memory, prior episodes, live tool queries, files, other agents, or cached summaries. Selection then becomes a budgeted optimization problem over these candidates.

Each candidate is a record with features that support scoring, constraints, and learning.

Objective

For a task state xxx with token budget BBB and latency budget LLL, choose a subset SSS of candidates (including executing some deferred queries) to maximize expected task utility.

This gives a principled greedy selector that balances “how good” with “how much” and “how risky.”

System components

  1. Task specifier
    Normalize the goal into a typed need profile: intent, constraints, required tools, allowed data scopes, budgets.

  2. Candidate generators

    • Memory retrievers: episodic, semantic, procedural.

    • Index retrievers: vector + symbolic + graph.

    • Tool planners: produce deferred_query candidates with EV and cost.

    • Cohort agents: proposals plus self-scores.

  3. Budgeter
    Set B,L,ρB, L, \rhoB,L,ρ per task and user policy. Reserve headroom for the model’s own reasoning.

  4. Selector
    Hybrid MMR + knapsack greedy:

    • Stage A: select a small set of deferred queries with the best EV per unit cost. Execute them.

    • Stage B: merge new results, then run submodular greedy to pick the final context set.

  5. Composer
    Populate a context blueprint with typed slots rather than dumping a flat blob.

Fill with compression operators: merge, summarize, distill, cite, dedupe. Respect slot caps.

  1. Critic and guardrails
    Check for leakage, stale facts, contradiction, and policy violations. If violated, evict or compress; never silently exceed budgets.

  2. Learner
    Update weights and thresholds from outcomes. Use counterfactual estimators over logs to learn better EV for deferred queries and better slot allocations.

Retrieval and scoring details

  • Relevance: intent-conditioned hybrid search. Score with a small cross-encoder, not cosine alone.

  • Actionability: does this item change decisions or enable a concrete step. Learn via credit assignment to items that were present in successful runs.

  • Reliability: provenance prior times recency calibration. Penalize ungrounded summaries unless citations are present.

  • Freshness: time decay with domain specific half-life.

  • Novelty: MMR diversity to avoid near-duplicates.

  • Sensitivity and scope: per-user tenancy, consent flags, and policy labels feed the risk constraint.

Pseudocode for the selector

python
def select_context(task, generators, budget):
    C = []
    for g in generators:
        C += g.propose(task)                 # includes memory, indices, deferred queries

    # Stage A: pick and execute a few high-EV deferred queries
    Q = [c for c in C if c.kind == "deferred_query"]
    Q_sorted = sorted(Q, key=lambda q: q.ev / (q.costs["latency_est_ms"]+q.costs["tokens_est"]))
    execd = []
    for q in Q_sorted:
        if budget.latency_left() >= q.costs["latency_est_ms"]:
            execd += execute(q)
            budget.consume(latency=q.costs["latency_est_ms"])
    C += execd

    # Stage B: submodular greedy under token budget and risk cap
    S = []
    while True:
        best = argmax(
            [marginal_gain(i, S, task) / token_cost(i) for i in C if feasible(i, S, budget)]
        )
        if best is None: break
        S.append(best); budget.consume(tokens=token_cost(best))
        C.remove(best)
    return compose(S, task.blueprint)

Why this answers your “unified” requirement

  • Memory and live data are first-class citizens with the same scoring, budgeting, and risk treatment.

  • The agent picks not just what to include, but which queries to run at all, based on expected value.

  • Context is structured into slots that the model can exploit, which improves efficacy per token.

  • The policy learns. Items that correlate with wins get higher expected value; noisy items decay.

Operational metrics

  • Efficacy per token: delta task success or reward per 1k tokens added to context.

  • Precision@k of retrieval and false recall rate.

  • Redundancy ratio: selected tokens that add no new unique facts.

  • Staleness rate: fraction of facts past their freshness half-life.

  • Leakage incidents and scope violations.

Anti-patterns to avoid

  • Treating the vector store as the memory rather than an index.

  • Executing all queries before deciding if their results fit the budget.

  • Unstructured concatenation of everything into the prompt.

  • Summarizing without citations or provenance.

Minimal worked example

Goal: “Plan coil-spring conversion options for a 2017 Cayenne S under Denver emissions.”

  • Generators propose:
    a) semantic memory items for user suspension preferences, emissions constraints.
    b) file chunks from prior build notes.
    c) deferred queries to two shops and one parts catalog.
    d) an episodic memory from a prior chat with costs and risks.

  • Selector executes one parts query with highest EV per ms, skips the other two due to budget.

  • Composer fills slots: constraints, user prefs, retrieved evidence with citations, and a short episodic note.

  • Critic flags an old note about AHC that does not apply, which is evicted.

  • Learner credits the parts catalog retrieval and the “preference” memory for improving plan quality, increasing their future weights.

This gives you a single, coherent mechanism that optimizes what the agent remembers, what it fetches, and what it finally says, all under the same objective and budget.

Critical tradeoffs and how to handle them

  • GraphRAG cost vs benefit. Global graphs are expensive and historically non-incremental. Solution: stream updates and limit graph work to neighborhoods and affected communities. Keep global summaries on a slow cadence. Reddit+1

  • Latency budgets. Plan deferred queries by expected value per ms. Enforce a reserved token headroom for the model’s own reasoning.

  • Multi-agent contention. CRDT or ledger first, human-readable consolidations later. Enforce role-based write policies and redaction.

Optimizers and metrics

Pick per-module metrics aligned to behavior and budget.

  • RankCandidates
    Metric: NDCG@k on human- or heuristic-labeled utility; penalty for redundancy and risk violations.
    Optimizer: MIPROv2 when you have ≥ a few hundred labeled contexts; else COPRO to improve instructions quickly; add BootstrapFewShotWithRandomSearch to tune examples when labels are sparse. DSPy+2DSPy+2

  • SummarizeForSlot
    Metric: faithfulness judged by citation overlap + a constrained factuality scorer on extracted triples; hard cap on tokens.
    Optimizer: MIPROv2 for joint instruction + demo tuning; COPRO for instruction-only on small sets. DSPy+1

  • EVofDeferredQuery
    Metric: correlation between predicted EV and realized task reward delta; auxiliary loss on latency calibration.
    Optimizer: COPRO to shape instruction; examples come from logged runs.

  • ConsolidateEpisode
    Metric: human approval rate on merges; reduction in future retrieval redundancy; provenance coverage.
    Optimizer: MIPROv2.

  • RedactForScope
    Metric: zero policy violations on a red-team test set; minimal utility loss compared to unredacted baseline.
    Optimizer: COPRO.

  • BlueprintFill
    Metric: downstream task success given same candidate set; enforce slot caps.
    Optimizer: MIPROv2.
